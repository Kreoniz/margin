## Verdict

The feature's product direction and core persistence design are acceptable. I found no P1/P2 defect, privacy regression, or reason to reopen the agreed compact Library design. There is **one independently reproduced P3 response-order defect**: a delayed media-completion acknowledgement can overwrite newer state already accepted from bootstrap, including a deliberate re-add to Up next. The latest guards fix the previously reported direction of the race but do not cover this reverse direction. Recommend addressing it with a targeted regression before considering the response-order work complete; it does not require another design round.

## Finding

### P3 — stale Done acknowledgement removes an already-observed, newly re-added priority

**Location:** `web/src/App.tsx:612–619` (`acknowledgeMedia`), called by `patchMedia` at line 623 and editor save at line 1607. Queue/bootstrap acceptance guards are at lines 217–225 and 523–530.

`acknowledgeMedia` accepts every returned Media, replaces the current row, and removes membership whenever that response says `done`. It does not check whether a newer media/queue snapshot has already superseded the response. Incrementing the request generation on acknowledgement prevents older reads from applying afterward, but does not make this acknowledgement newer than an already accepted read. `latestQueueVersion` is never consulted on this path.

**Reproduction independently executed in Chromium against the existing production assets, with all requests intercepted and fictional records:**

1. Initial queue version 1 is `[book, video, game]`; all three are pending.
2. In tab A, mark `book` Done. Model the server committing that mutation (queue version 2), but hold its HTTP response. The response contains `book.status = done`, `updated_at = 2026-11-07T00:00:01Z`.
3. Model another owner tab returning that item to pending and explicitly adding it again. Its pending media has `updated_at = 2026-11-07T00:00:02Z`; queue version 3 is `[video, game, book]`. This is an explicit add, not automatic reprioritization by Undo.
4. Dispatch the existing focus refresh in A and deliver that consistent version-3 bootstrap. Assert that A now displays `book` at **#3**.
5. Make subsequent bootstraps fail with 503, then release the older Done response.

**Observed:** before release, ranks are `#1, #2, #3`. After release, only `video` and `game` remain in Up next. The old response replaces the newer pending media and filters `book` out of the already accepted version-3 queue. The failed refresh leaves the incorrect display in place. The server's version-3 queue has not been changed by this acknowledgement; a later successful refresh repairs the UI. This is therefore a client reconciliation problem, not durable data loss. It is in the feature's new priority-cleanup path even though general stale media-response handling predates the feature.

**Smallest correction:** freshness-check media acknowledgements before replacing status **and** applying priority cleanup. A response known to precede the currently accepted media state must not remove that state's membership or invalidate newer reads. The existing `updated_at` values distinguish the reproduced ordering, but do not assume transaction-start timestamps provide a strict ordering for every concurrent write; an owner-only transaction/queue revision is the stronger option if needed. Preserve the existing immediate cleanup when no newer state is known. Add this reverse-order case alongside the delayed-queue tests, including failed refresh. Fixing only the membership filter is insufficient because `selectUpNext` also excludes media wrongly restored to Done.

## Assessment across the scope

- **Durability and concurrency:** the singleton queue lock, expected version check, append/swap/no-op semantics, and transactional completion/deletion cleanup are coherent. Queue lock precedes media locks in the changed application writers; browser capture takes its independent token/URL gates first. Development fixture cleanup removes membership before deleting media. The repeatable-read, read-only bootstrap transaction correctly keeps the queue and media at one database snapshot. A rewrite of the small shortlist on effective changes is proportionate to this product; no rank-allocation framework is warranted.
- **Latest acknowledgement fix:** version checks reject older queue snapshots; cleanup-generation checks reject delayed queue success/conflict responses after local cleanup, even without a successful bootstrap. Media acknowledgements now invalidate earlier bootstrap requests, and editor Done uses the centralized cleanup. I independently verified both an older bootstrap arriving after a queue removal and an editor Done racing with a delayed queue acknowledgement, with refresh failures. Both passed. The finding above is the opposite response direction, which the new tests do not cover.
- **Auth and privacy:** the new routes go through existing owner-session and same-origin mutation middleware. Priority remains a separate owner DTO/table, not a Media field, so unchanged public/MCP/export/capture representations do not inherit it. Browser credentials can cause the existing Done operation and transactional cleanup but do not gain queue read/reorder authority. No new access capability or dependency was introduced. These are static findings, not a fresh penetration test.
- **Capture defaults:** removal of blanket flags is narrowly placed in browser and submission preparation. MCP save reuses the latter. Unresolved title-only ISBN handling remains in `prepareMedia`; duplicates retain existing data and flags. Automatic source behavior remains unchanged as agreed. There is no migration that silently clears old flags or automatically populates priority.
- **Library usefulness:** the six final desktop/mobile captures preserve recognizable artwork and titles; Library remains the default, with the same three layouts and discreet contextual controls. The rank/chevron outline makes the affordance easier to distinguish without a permanent action panel. Grouped layouts deliberately put type structure before global order; the visible ranks and List alternative make that tradeoff explicit. The mobile top viewport still shows few items, but this largely reflects the retained artwork/shelf layout rather than a new dashboard. I would not demand another layout redesign on this evidence.
- **Keyboard, focus and filters:** static tracing supports native Tab/Enter/Space actions, Escape return, focus transfer to a stable row before removal/reorder, queue-popover suppression of global shortcuts, both status-cycle directions, and `g n`/`#next`. Filtering preserves queue order and disables moves under ambiguous subsets. The empty Channels shortcut now checks that a trigger exists; the disappearing picker and last-chip paths recover to search. The documented Library-return exception is intentional and internally consistent, not a new defect.
- **Complexity and retained features:** no added package or stack change. Discover, Sources, existing sharing and integration controls remain. The implementation is concentrated in the existing library rather than adding a separate priority destination. The extra response guards have a concrete reason, though their asymmetry needs the correction above.
