## Finding

**P2 — A delayed Done acknowledgement can overwrite a newer bootstrap and remove a deliberately re-added item locally.** `web/src/App.tsx:612-619` unconditionally applies an acknowledged media object, increments the cleanup generation, and filters its ID from the current queue. Unlike queue acknowledgements, it does not establish whether a bootstrap already observed a later state. Reproducible ordering: tab A sends Done for queued item X; the server commits, but its response is delayed. Tab B returns X to unfinished and explicitly adds it back to Up next. A refresh in tab A receives the later consistent bootstrap with X pending and queued at a newer queue version. Then A's old Done response arrives, replacing X with the older done object and removing X from the newer queue in memory. If the ensuing bootstrap fails, A shows the wrong status and priority until a later successful refresh; even if it succeeds, the view can visibly regress in the meantime. The server's actual queue remains intact, and expected-version checks prevent a stale queue write from overwriting it. This is a code-path analysis, not an independently executed browser reproduction.

Smallest robust direction: associate the media mutation response with an authoritative ordering token/snapshot (including the queue version after transactional cleanup) and do not apply its media or cleanup against a demonstrably newer accepted snapshot; ensure equal-version cases account for media changes too. Add a targeted intercepted-response test for Done, remote return/re-add, newer bootstrap, then delayed Done acknowledgement with failed refresh. Merely extending the current cleanup-generation guard to queue replies does not cover the reverse ordering.
