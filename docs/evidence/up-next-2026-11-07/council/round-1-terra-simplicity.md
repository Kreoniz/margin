## Optional UX improvements, not defects

1. **Make the rank's action affordance clearer if owner testing shows hesitation.** In `web/src/App.tsx:810` a queued item's action is displayed as only `#2` (with a helpful accessible name and title); in `after-next-desktop.png` and `after-next-mobile.png` it resembles the adjacent `Up next · #2` metadata more than a control. A first-time mouse or touch user may not infer that tapping the rank opens reorder and remove actions. A subtle button treatment or small action glyph, retaining the 44px target and accessible name, could make that path easier to discover. The existing + Next label, help text, and popover mitigate this; this is a visual judgment, not a demonstrated failure. Avoid adding a permanent action strip.
2. **Mobile overview density remains a tradeoff.** In `after-mobile.png` the heading, layout selector, search, Quick Find, filters, tabs and section jumps occupy roughly the first half of the 390px viewport; only one card is visible. The artwork remains recognizable and the controls are reachable. Consider a small toolbar reduction only after observing actual use; do not remove filters or layouts on this evidence alone. The fixture has very few visual items, so its whitespace is not representative of a fuller library.

## Contract and regression assessment

The code appends explicit adds, performs global neighbor swaps, uses the queue order in List and preserves per-section order in grouped views. It disables moves for the specified filtered/subset cases, and surfaces recovery guidance. Completion and deletion take the queue lock and remove membership in the same transaction; Undo restores status only. Owner bootstrap reads media and queue under repeatable read; stale writes return the current version. Capture and submission stop creating routine attention flags, while unresolved ISBN handling remains. Existing flags are not broadly cleared. Queue data stays separate from public/integration DTOs; owner routes remain behind existing session and same-origin middleware. Discover, Sources and sharing remain present. These are static code conclusions, not fresh end-to-end proofs.

One useful future regression case is a real-backend sequence combining a priority write with completion or deletion from another owner tab and then retrying a conflict, checking both visible ranks and database membership. Existing reported race and synthetic coverage reduces the urgency; this is a coverage suggestion, not evidence of a bug. Also check the rank control with a screen reader or real touch user before treating automated axe and geometry results as comprehensive accessibility proof.
